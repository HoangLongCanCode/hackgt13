# AGENTS.md: guide for AI coding agents and new teammates

This is the canonical guide for AI coding tools (Claude Code, Cursor, Codex, GitHub Copilot) and for people joining the
AI Spatial Driving Copilot, the HackGT 13 prototype by Knuckle Sandwich Robotics Inc. (KSR). Read it before editing.
`CLAUDE.md` and `.github/copilot-instructions.md` only point here.

## The rules that matter most

1. **The protocol has one source of truth:** [`contracts/PROTOCOL_v2.md`](contracts/PROTOCOL_v2.md), with one JSON
   Schema per message in `contracts/schemas/` and golden samples from real runs in `contracts/samples/v2/`. A protocol
   change updates the spec, the schema, the samples, the Python producer and the Kotlin consumer in the same change.
2. **The overlay contract is [`driving_assist/ENGINEER_A.md`](driving_assist/ENGINEER_A.md):** `VisionData` in 0..1
   overlay space, `RouteState(time, action, audio, ui)` from the route engine. Do not fork the overlay or the layout.
3. **No route logic in the Android app or in the relay.** Maneuvers, progress, ETA and spoken text come from phase1
   (`src/phase1/` on branch `phase1`). The app only displays phase1's output and combines it with perception.
4. **Never block the camera thread, and always close `ImageProxy`** in a `finally` block. Drop frames that have no
   credit; never queue them.
5. **`MOCK` mode must keep working.** `MockDataViewModel()` must stay constructible with no arguments, and
   `MockVisionSource` and the 5 s route loop stay. `gradlew.bat :app:assembleDebug` must pass with no laptop.
6. **Tom owns the app UI.** Keep edits to his files minimal and backward compatible, and list every touched file of
   his in the PR description.
7. **Display only (plan section 38).** No output may steer, brake or accelerate, and no LLM sits in a safety path.
   `UNKNOWN` stays unknown, `GREEN` is never permission, and stale perception suppresses object alerts.
8. **Nothing large or secret in git:** no weights, videos, datasets, APKs, build folders, `outputs/`, `.env` files or
   API keys. No absolute machine paths in code or docs: use relative paths, env vars or CLI flags.
9. **Run Python from `perception_engine/`** with the project venv, and `import torch` before `onnxruntime`.
10. **Agents: do not run `git commit`, `git push`, `git reset` or branch switches unless your user asks.**

## Coordinate, unit and time conventions

| Quantity | Convention |
|---|---|
| Server image space | Every `bbox`, lane point and road point in `perception.frame` / `perception.update` is in pixels of the **upright analysed image**: `(0, 0)` top-left, x right, y down, size `image.width` x `image.height`. Live frames are rotated by the uplink `rotationDegrees` first, and scaled down if wider than 1280 px |
| `bbox` | `[x1, y1, x2, y2]` pixels (corners, not width/height) |
| Lane polylines | `laneBoundaries` left to right, up to 20 points each, lanes numbered `1..laneCount` from the left. Points are extrapolated and can lie outside the image (x from -0.25 W to 1.25 W): clip before drawing |
| Overlay space (app) | `VisionData` boxes are `[x, y, w, h]` as 0..1 fractions of the **view**, top-left plus size. The preview is `FILL_CENTER` (cover and crop). `VisionMapper` maps server image space to overlay space with `PreviewCoordinates` at rotation 0 |
| CameraX buffer space | `ImageProxy` buffer before rotation; `rotationDegrees` = rotate clockwise by this to make the image upright. Only on-device detectors (the ENGINEER_A path) map from here |
| Ground plane | Metres. `distanceMeters` = forward distance from the camera to the object's nearest face. `lateralMeters` and `groundXZ[0]`: + = right of the camera axis. `groundXZ[1]` = forward. Flat-ground assumption |
| Track ids | Integers, stable within one `sessionId` only. Traffic lights and signs have ids >= `staticIdOffset` (1,000,000) |
| `ptsSeconds` | video / sim: the clip's container pts (what the tablet player reports). live: `(captureTimeNs - first captureTimeNs of the session) / 1e9` |
| `captureTimeNs`, `clientTimeNs` | Tablet clock (`SystemClock.elapsedRealtimeNanos` base), echoed back so the tablet measures latency on its own clock. No clock sync is needed |
| `serverTimeMs` | Laptop Unix epoch ms. Never compare it with tablet clocks |
| `timestampMs`, `tripTimestampMs` | GPS fix time, Unix epoch ms (the phase1 trip clock) |
| `heading` | Degrees clockwise from north; 0 when unknown |
| `VisionData.time`, `RouteState.time` | Seconds. LIVE: since the first uplinked frame. SIM: the clip's media time |

## Build, run and test

In the Python blocks, `python` means the project venv interpreter. Either call it directly
(`.venv\Scripts\python.exe` on Windows, `.venv/bin/python` on Linux) or activate the venv first
(PowerShell: `Set-ExecutionPolicy -Scope Process Bypass; .venv\Scripts\Activate.ps1`; Git Bash:
`source .venv/Scripts/activate`). On Windows never call a bare `python3`: it is the Microsoft Store alias.

## Invariants and do-not rules

**App (Tom's shell)**
- Keep `sensorLandscape`, `PreviewView.ScaleType.FILL_CENTER`, package `com.drivingassist.glass`, `compileSdk 35`,
  AGP 8.7.3, Kotlin 2.0.21 and JVM 17. Do not pull in libraries built for newer Kotlin.
- `MockDataViewModel` keeps `@JvmOverloads` and its no-arg constructor; `MockVisionSource` and the route loop stay.
- The analyzer (camera thread, `STRATEGY_KEEP_ONLY_LATEST`) checks `canUplinkNow()`, encodes, calls
  `offerCameraFrame`, and returns. No network waits, model loads or locks held across I/O. `image.close()` in `finally`.
- ExoPlayer is touched on `Dispatchers.Main` only. Bridge coroutines run on `Dispatchers.Default`.
- Draw nothing stale: when `perceptionStale` is true, vision lists are empty and the UI says so.
- MOCK looks exactly like Tom's app: the status chip and `PerceptionHostEffects` are composed only for LIVE / SIM, and a
  plain launch uses the BuildConfig source (launch extras apply to one launch unless `ksr.persist` saves them).
- LIVE needs `OUTPUT_IMAGE_FORMAT_YUV_420_888` in `CameraPreview` (the JPEG encoder takes YUV only).

**Protocol and server**
- Every uplinked KSR1 frame (24 bytes or more) gets exactly one wave-1 answer: a `perception.frame` with a matching
  `echo.frameId`, or a `perception.skip`. Clients never exceed `uplink.maxInFlight`.
- Clients reset per-session state (tracks, sim buffer, lanes) on every new `sessionId`; credits come back through the
  server's answers to the frames in flight, so they are reset only when the socket is lost.
- Only the controller (`perception.hello.role`) uplinks, reports playback and feeds live navigation. A watcher ignores
  live / sim results (they are another client's stream). The Kotlin bridge does this (`LinkStatus.takenOver`) and
  re-sends its hello when the server goes idle.
- The server's asyncio loop never touches torch. Each model is owned by exactly one lane thread (fast: detector,
  trackers, light classifier; slow: depth, lanes, signs, segmentation).
- `inEgoPath` is decided on the server (`wire.py` `EgoPath`); the Kotlin Driving Context picks the lead from it.

**Perception engine**
- `import torch` before creating any onnxruntime session, or ORT silently falls back to the CPU.
- `YOLO_AUTOINSTALL=False`. Do not `pip install` ad hoc: change `requirements.txt` pins as described in `SETUP.md`
  section 8, keeping torch from the cu130 index.
- Do not edit vendored code in `perception/third_party/`; pin a new commit in `scripts/fetch_third_party.py`.
- New or changed weights go through `scripts/download_models.py` (`ITEMS`, with size and sha256) and the block's
  `MODELS.md`.

**Navigation**
- The relay (`nav/relay_core.js`) only calls phase1 exports. Bugs in route behaviour go to the phase1 owners; do not
  patch around them in the app.
- Never commit a Google key, a `.env` file, or a real captured GPS session (it is location history); keep real
  sessions under the gitignored `perception_engine/data/`.

**Repo**
- Gitignored and never committed: `perception_engine/{models,data,outputs,perception/third_party,.venv,.cache}`,
  `*.pt`, `*.pth`, `*.onnx`, `*.safetensors`, `*.mov`, `*.mp4`, `driving_assist/**/build/`, `*.apk`,
  `local.properties`, `.env`.
- BDD100K, KITTI, Cityscapes and LISA are non-commercial; derived files (masks, crops, frames) inherit that.

## Current status, known gaps and next tasks

**Works today** (tested 2026-09-26 on the dev laptop, RTX 5060 Laptop):
- Server in video, sim, live and auto modes, protocol v2 with credits, sessions, two waves, stats, `/health`.
- phase1 navigation relayed in sim (by media time) and live (by `client.trip_state`), with crash recovery.
- Kotlin bridge, Driving Context and app mapping; the APK builds; all test suites above pass.
- End to end with the JVM fake tablet (localhost): SIM 12.5-16 results/s with results 90-190 ms ahead of display;
  LIVE capture-to-result 106-114 ms p50 / 141-162 ms p95 at about 13-17 results/s. Details and caveats:
  `docs/perception/examples/`, `docs/perception/RUNBOOK.md`.

**Known gaps**
1. Not run on a Tab S9 yet: camera uplink, ExoPlayer playback, GPS, on-device JPEG cost and thermals are untested on
   hardware.
2. Live latency is above the 100 ms target at `maxInFlight 2`. The fast lane takes about 32 ms alone but 52-60 ms while
   the slow lane runs in the same Python process (GIL/CPU contention, GPU about 50 % busy). `--max-in-flight 1` gives
   74-91 ms p50 at 10-11 fps; `--set slow.max_hz=5` saves about 10 ms.
3. The first 1-3 s of every session are slow (sim results late, then look-ahead overshoot; live 0.6-1.1 s for the first
   frames). The Driving Context shows STALE meanwhile.
4. Following-distance thresholds are not speed-aware (CRITICAL below 7 m, cleared above 9 m); stopped behind a car it
   stays TOO CLOSE. About 8 `VEHICLE_TOO_CLOSE` events per 31 s remain on the dense city clip.
5. The `EgoPath` corridor yaw from the lanes anchors is noisy at intersections (hits the 8 degree clamp); lanes and
   camera horizons can disagree by about 30 px. Temporal smoothing would help.
6. Close-range depth on truncated boxes can read low (1.1-2.2 m for parked cars beside the ego car).
7. `PreviewCoordinates.rotateNormalized` may have its 90/270 cases swapped (Tom to confirm in DEBUG; the perception
   path always uses rotation 0).
8. `exitSigns` is always empty (no exit-sign detector); signs cover stop, yield, speed limit, do-not-enter and
   pedestrian crossing only.
9. Camera intrinsics: the app's `focalPx` ignores `LENS_INTRINSIC_CALIBRATION`; BDD clips have no intrinsics (default
   700 px at 1280 wide, while the openpilot block's lane-speed check implies about 1140 px), so absolute distances on
   clips scale with that assumption.
10. phase1 behaviours passed through unchanged: `ARRIVE` is announced hundreds of metres early, turn audio is upper-case,
    `START_ROUTE` never appears, no re-routing when `offRoute`. The Google provider is untested (no key), and the demo
    navigation sessions are synthetic (they do not match the video).
11. SIM orientation on the device is unverified: BDD clips are 720x1280 frames with a -90 degree display matrix, and the
    overlay assumes ExoPlayer shows them as 1280x720 landscape (check once in DEBUG; pre-rotate the clip if not).
12. `perception/common/video.py` `VideoFileInput` stamps each frame with the previous frame's pts (offline tools only;
    the server uses its own `ClipReader`).
13. Sim over Wi-Fi uses a fixed `--sim-margin` (0.10 s); tune it on the real hotspot.
14. Licences: the realtime defaults are research/demo only (see `docs/perception/MODELS_AND_LICENSES.md`).
15. The perception loops stop only with the ViewModel: in the background the WebSocket stays open (the tablet stays the
    laptop's controller), although the overlay loops idle and GPS pauses while the activity is stopped.

**Next tasks** (roughly in priority order)
1. Tab S9 bring-up: LIVE over USB and SIM with a pushed clip; measure capture-to-result, JPEG cost and thermals; check
   overlay alignment in DEBUG.
2. HUD work from `PERCEPTION_INTEGRATION.md` section 11: light icons, alert emphasis, lane guidance, TTS, stale banner.
3. Start SIM playback only after the first result arrives; warmer initial look-ahead.
4. Live latency: process-per-lane server, or tune `slow.max_hz` and `maxInFlight` on the device.
5. Speed-aware following distance; smooth the ego-path yaw.
6. Merge `phase1` into `main` (the relay then finds it with no flags; see `docs/perception/INTEGRATION_PHASE1.md`).
7. Record a real session (android-collector GPS + dashcam video) for SIM navigation; add a Google key locally for live

## Environment gotchas

- The server takes about 30-60 s to load and warm up (26-54 s measured); warm-up briefly peaks at about 5 GB of VRAM.
  Keep other GPU jobs small.
- Run on AC power: on battery the laptop GPU is about 20-30 % slower.
- FastAPI with `from __future__ import annotations` needs `WebSocket` imported at module level in `server.py`,
  otherwise every WebSocket upgrade fails with HTTP 403.
- `perception_engine/tests/__init__.py` exists because some venvs ship an unrelated top-level `tests` package; run
  tests as `python tests/<file>.py` from `perception_engine/`.
- The onnxruntime CUDA EP pays about 22 ms per input-shape change (the light classifier runs fixed batches of 8).
- Git Bash splits `platforms;android-35` at the `;`: give `sdkmanager` a `--package_file` instead.
- `local.properties` needs forward slashes in `sdk.dir`.
- Windows Firewall asks to allow `python.exe` the first time the server listens on Wi-Fi: allow private networks.
